# 研讨会收入归因分摊库

Go 实现的内存计算库：把一个完整统计批次的已成交商机收入，按等权归因分摊到影响成交的多场研讨会，并生成可追溯报表。

## 业务规则实现

- **等权归因**：一笔商机在每个关联研讨会上的理论归因额 = 成交金额 ÷ 关联研讨会数；未关联研讨会不得获得该笔收入。
- **逐笔守恒**：每个关联项只取理论额的向下/向上取整值，每笔商机的实际分摊合计精确等于成交金额。
- **汇总边界**：每场研讨会的实际汇总只能是其理论汇总（精确有理数累计）的向下/向上取整值；理论汇总恰为整数时必须等于该整数。该要求与逐笔守恒同时成立。
- **确定性**：内部先按标识排序再求解，同一输入集合（与商机顺序、关联顺序无关）必然得到相同结果。
- **筛选视图**：完整报表、单笔商机查询、选定研讨会汇总对应同一份分摊结果；筛选只影响展示，不重新分配收入。

## 算法

每笔商机分摊归结为：每项先取 `floor(金额/k)`，再把 `金额 mod k` 个 +1 余数分给部分关联研讨会。对每场研讨会，余数个数必须落在 `[floor(d), ceil(d)]`（`d` 为该场理论汇总的小数部分之和，以 1..10 的最小公倍数 2520 为公分母做精确整数累计，无浮点误差）。

余数分配建模为带下界的可行流（Dinic 最大流）：

- 源 → 商机：下界 = 上界 = 该笔余数个数
- 商机 → 研讨会：容量 1（每项至多向上取整一次）
- 研讨会 → 汇：下界/上界 = 该场允许的余数个数区间

约束矩阵全单位模且分数解（每项取理论小数部分）恒存在，因此整数可行解必然存在；固定的排序与建图顺序保证结果确定。

## API

```go
import "attribution/attribution"

report, err := attribution.GenerateReport(deals) // deals: []attribution.Deal
report.Allocations()                 // 完整批次分摊明细
report.Summaries()                   // 完整批次研讨会汇总
report.DealAllocations(dealID)       // 单笔商机分摊
report.SeminarSummary(seminarID)     // 单场研讨会汇总
report.SeminarSummaries(ids)         // 选定研讨会汇总（筛选视图）
```

理论汇总以 `TheoreticalFloorCents + TheoreticalRemNum/TheoreticalRemDen` 精确表示。

## 运行测试

```sh
go test ./...          # 全部测试（含满规模性能测试）
go test ./... -short   # 跳过性能测试
go test ./attribution/ -run TestPerformance -v   # 仅性能测试，输出耗时与峰值内存
```

测试覆盖：验收三角案例（三笔 1 美分、AB/BC/AC）、混合关联数量、理论汇总恰为整数、互不相连多组关联、大金额（至 10^12 美分）、乱序不变性、筛选视图一致性，以及用 `math/big.Rat` 独立精确核对每个关联项取值范围、逐笔守恒与每场汇总边界。

性能测试在子进程中以 50000 商机 / 5000 研讨会 / 300000 关联运行，核对全部金额约束，并通过 `getrusage` 记录峰值内存。本机实测：报表生成约 0.12 秒（上限 20 秒），峰值内存约 146 MiB（上限 256 MiB，含测试进程与输入数据本身）。
